# Address resolution

Courier Router больше не использует один ответ `clean/address` как безусловную истину для DaData.

## Pipeline

1. Консервативная предобработка строки:
   - `СПБ` / `ПБ` в начале -> `Санкт-Петербург`;
   - `ЛО` в начале -> `Ленинградская область`;
   - исправление известной рабочей опечатки `Коменданский` -> `Комендантский`;
   - нормализация пробелов и разделителей.
2. `suggest/address` с `count=5`.
3. Для Санкт-Петербурга и Ленинградской области используется `locations_boost`.
4. Каждый кандидат оценивается по структурным компонентам:
   - город/регион;
   - улица;
   - дом;
   - корпус;
   - наличие координат.
5. Кандидат принимается автоматически только если score достаточно высокий и есть отрыв от второго кандидата.
6. Иначе выполняется fallback на `clean/address`, но результат также проверяется тем же component score.
7. Сильное расхождение, например исходный Санкт-Петербург -> найденный Сосновый Бор, блокирует построение маршрута без явного override.

## Cache migration

Старые записи кэша с provider=`dadata`, созданные до resolver-а, автоматически переоцениваются при первом следующем использовании. Это важно, чтобы уже закэшированный неверный адрес не пережил обновление алгоритма.

Новые записи имеют provider `dadata_suggest` или `dadata_clean` и сохраняют диагностическую секцию `_resolver` в `raw_json`.

## Diagnostics

`geocoding-report.json` содержит:

- `resolver_status`;
- `resolver_score`;
- `resolver_reasons`;
- `resolver_query`;
- до пяти `resolver_candidates`.

Это позволяет понять не только итоговый confidence, но и почему был выбран конкретный адрес.
